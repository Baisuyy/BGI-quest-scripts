# 任务点与地图指引：能不能靠它走到任务目标

结论先说：**可行，而且不是从零做——BGI 里躺着一套写完又被下线的「自动追踪」，325 行，链路完整。**

官方把功能页 `feats/task/track.html` 删了（现在 404），`OnSwitchAutoTrack` 标了 `[Obsolete]`、启动代码整段注释。所以这不是"没人想到"，是"想到过、做出来过、后来撤了"。撤的原因从代码里能看出来，见第 4 节。

## 1. 你观察到的两个东西，在代码里分别是什么

| 你看到的 | 代码里的对应物 |
|---|---|
| 追踪任务后，大地图上有一个任务点 | `AutoTrackTask.TrackMission()`：按 J 开任务界面 → 点「追踪」→ **打开地图时中心点就是任务点** |
| 屏幕上有地图指引 | `BlueTrackPoint`：按 V（`GIActions.QuestNavigation`）后目标处出现的蓝色光点，模板 `blue_track_point_28x.png`，阈值 0.6 |

也就是说，这两个信号 BGI 都处理过，只是没接到 UI 上。

## 2. 三条可用信号，各自能拿到什么

### 信号 A：任务面板的距离数字（OCR）

追踪任务时，左上角小地图下方的任务条会显示「任务名 / 当前目标 / 156m」。

- 位置：`AutoTrackTask.OcrMissionTextRaList()` 取派蒙菜单下方 `300x100`；特别版的 `quest.tracker()` 取 `(28,118,430,190)`，两者都覆盖这块
- 解析：找长度 < 8 且含 `m` 的文本，`StringUtils.TryExtractPositiveInt()` 取数字
- 精度：±1m，游戏给的是整数米
- 限制：**只有追踪中才有**；目标在视线内时数字会消失或变成「已到达」

价值：给"还剩多远"一个绝对量，是判断"到了没有"的唯一便宜手段。

### 信号 B：大地图任务点（地图坐标）

两条取法，成本差一个数量级：

| 取法 | 做法 | 成本 |
|---|---|---|
| B1 读地图中心 | 点追踪 → 开地图 → `genshin.GetPositionFromBigMap()` | **零模板**，但依赖"地图会自动居中到任务点" |
| B2 模板匹配 | 截大地图 → 匹配任务图标 → `(像素-中心)×zoom/scale + 中心坐标` | 要实机裁模板，要处理多任务叠加与缩放 |

B1 的关键依据是原作者写在代码里的注释：

```csharp
// 距离大于150米，先传送到最近的传送点
// J 打开任务 切换追踪打开地图 中心点就是任务点
```

B2 的比例公式在地脉花里已经验证过（`AutoLeyLineOutcropTask.LocateLeyLineOutcrop`）：

```csharp
_leyLineX = (960 - flower.X - 25) * mapZoomLevel / mapScaleFactor + center.X;
_leyLineY = (540 - flower.Y - 25) * mapZoomLevel / mapScaleFactor + center.Y;
```

`center` 来自 `GetBigMapCenterPoint()`（SIFT 把当前大地图与底图对齐），`mapZoomLevel` 是 1.0–6.0 的缩放级别。**所以"屏幕像素 → 世界坐标"这条路是通的，不需要米游社坐标标定**——上一轮锚点卡住的那个问题，在游戏内截图这条路上不存在。

### 信号 C：屏幕上的蓝色导航点（V）

- 按 V → 屏幕中部出现蓝点 → 模板匹配拿到像素位置
- 用像素偏移调整镜头朝向，对准后按 W 前进，循环
- 精度：方向准，距离靠信号 A 补
- 限制：只在目标进入导航范围（约 150m 内）时出现；不是所有任务都有导航点（纯对话/交付类没有）

## 4. 官方为什么撤掉

不是识别不了，是流程太糙。从代码能直接读出四个问题：

1. **一次性流程，没有循环**。`TrackMission()` 跑完就结束，失败只打日志，不重试
2. **没有到达判定**。`MakeBlueTrackPointDirectlyAbove()` 的退出条件写的是"对准了就算到"，之后又补了一句"到达目标"就 `break`，注释和代码互相矛盾
3. **传送依赖未校验的假设**。距离 ≥150m 时直接点「追踪」再找屏幕上最近的传送点图标，没有验证地图是否真的居中、点的到底是不是任务附近
4. **蓝点丢了就空转**。`else` 分支只打印"未找到追踪点"，然后继续 `while` 循环，鼠标每 100ms 抖一次

这四条都是"状态机缺失"的表现，不是能力缺失。补上状态机就有可用性。

## 5. 三个必须实机验证的假设

写代码之前先测，别先写：

| # | 假设 | 怎么测 | 不成立怎么办 |
|---|---|---|---|
| 1 | 打开大地图时默认居中到追踪的任务点 | 追踪一个远处任务 → 按 M → 看地图中心是不是任务 | 退到 B2 模板匹配，或 OCR 点左侧任务列表 |
| 2 | 任务图标能稳定模板匹配 | 截 5 张不同缩放/不同任务数的大地图 | 固定缩放到 3.0 再匹配，图标尺寸就固定了 |
| 3 | V 键导航点所有任务都有 | 挑 10 个不同类型任务（对话/采集/击杀/交付）各按一次 V | 对没有蓝点的任务退化到"小地图边缘方向 + 距离" |

第 1 条是方案 B1 的全部前提，最值得先测。

## 6. 建议的实施顺序

**阶段 0（半天，只读，零风险）**
给 `quest.tracker()` 加距离解析（约 10 行：正则 `(\d+)\s*m`，取最靠下的匹配），写一个探针脚本，追踪 10 个任务，记录「标题 / 步骤 / 距离」三列。目的是确认 OCR 稳不稳，而不是确认能不能读。

**阶段 1（1–2 天）**
把 `AutoTrackTask` 接到独立任务（恢复 `OnSwitchAutoTrack` 的启动代码），但改成状态机：

```
Idle → 读距离 → 远(≥150m) → 传送流程 → 校验落地 → 近(<150m) → V 导航 → 蓝点跟随 → 距离≤3m → 到达
                                    ↑失败重试 2 次            ↑蓝点丢失 3 次 → 回退小地图方向
```

**阶段 2（3–5 天，收益最大）**
大地图任务点 → 世界坐标 → 生成 8m 加密的直线路线 → 交给 `PathExecutor`。这一步的价值是**接上已有的东西**：

- 卡死有 `TrapEscaper`，再不行有刚做的内置 AI 接管
- 能断点续跑、能进调度器、能和现有 270 段录制路线混排
- 走不通时降级到阶段 1 的蓝点跟随

**阶段 3**
把阶段 2 跑出来的任务点坐标回流成数据，补前四章缺坐标的 161 个任务。

## 7. 对主线脚本意味着什么

上一轮的结论是"前四章没有坐标，所以没有路线"。任务点识别正好补这个洞，但要分清它补的是什么：

| 补上了 | 没补上 |
|---|---|
| 任务目标点的世界坐标 | 从锚点到目标点的可走路线 |
| 目标点会随任务进度移动（每次读都是最新的） | 地下/分层地图（层岩、渊下宫）仍不支持 |
| 区域内多个任务的先后关系 | 到达后的交互（对话、拾取、战斗）——这部分 `AutoSkip` / `AutoPick` / `AutoFight` 已有 |

所以现实的做法是：**任务点给终点，直线加密给路线，AI 接管兜底，交互交给现有实时任务**。这条路能跑通，但不保证 100% 到达——山区、洞窟、错层仍会失败，失败就重试或跳过，这正是内置 AI 接管存在的意义。

---

## 8. 风险

- 任务点是**区域型**时（如"调查某区域"），大地图只有一个圈，圆心不等于可交互点
- 任务点可能在地下，直线走过去会在崖边卡住
- 多个任务同时追踪时，大地图上图标会重叠，模板匹配可能选错
- 任务面板距离在部分任务里不显示（纯剧情/对话）
- 依赖小地图锁定方向、16:9、≥1080P——这些是 BGI 全局前提，不是本方案新增

---

## 9. 一句话回答"值不值得做"

值得，但顺序要对：**先花半天验证假设 1，再花两天把废弃的自动追踪接成状态机，最后才去做"坐标 → 路线"的自动化**。反过来做，会先写一堆模板匹配代码，然后发现地图根本不居中。
