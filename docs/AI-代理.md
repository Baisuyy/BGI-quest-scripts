# 大模型怎么参与跑图

一句话：**BGI 负责「看见」和「动手」，模型只负责「往哪走、做什么」。**

> **重要：这部分能力已经内置进 BGI 特别版内核。**
> 跑图卡死时由 BGI 自己接管角色，不需要装脚本；配置入口是 *任务设置 → AI 智能决策（内置）*，
> 说明见 [`Docs/AI-内置决策.md`](https://github.com/Baisuyy/BGI-quest-scripts/blob/bgi-special/Docs/AI-内置决策.md)。
>
> 本目录下的 [`js/_tools/ai-agent`](../js/_tools/ai-agent) 只是**脚本侧的可选实现**：
> 当你想在某个脚本里自定义决策逻辑（而不是跑图救援）时才用它，默认不联网、纯规则。

## 内置与脚本的分工

| 场景 | 用谁 |
|---|---|
| 跑图卡死、要脱困 | 内置（自动，无需脚本） |
| 脚本里按任务文字选路线、临时开关功能 | 脚本侧 `ai.Chat()` 或本目录工具 |
| 需要模型看到整张截图 | 内置的 `VisionMode`，或脚本自己发图 |

## 三层分工

| 层 | 谁做 | 具体接口 | 每步开销 |
|---|---|---|---|
| 感知 | BGI 内置识别 | `genshin.GetPositionFromMap()`、`Bv.WhichGameUi()`、`Bv.FindF()`、`quest.Tracker()` | 10–50 ms，0 token |
| 决策 | 规则 → 拿不准才问模型 | 本地规则函数 / `/chat/completions` | 0 或 200–400 token |
| 执行 | BGI 原语 | `pathingScript.Run(json)`、`genshin.Tp()`、`Bv.FindFAndPress()` | 由路线长度决定 |

感知层吐出来的是**结构化数据**，不是图片：

```json
{"pos":{"x":2280,"y":-820},"ui":"MainUi","hint":"对话","quest":{"step":"前往蒙德城"}}
```

模型拿到这几十个字节就能决策，不需要看屏幕。

## 为什么能省掉图像识别

| 做法 | 单次输入 | 延迟 | 20 步总消耗（量级） |
|---|---|---|---|
| 整屏截图 → 多模态 | 约 1.5k–2k visual token | 3–8 s | 3–4 万 token |
| 内置识别 → JSON 文本 | 200–400 token | 0.5–2 s | 5 千–1 万 token |

差一个数量级，且前者还要传图（脚本 `http` 没法直接发二进制，得先落盘再编码）。

真正贵的是「让模型自己看图找 NPC」这类开放任务。**有明确目标的移动、交互、战斗，都不该用视觉模型**——BGI 的小地图模板匹配和 UI 判定又快又准。

## 两个开关

`config.json`：

```json
{
  "ai":     { "enabled": false, "endpoint": "http://127.0.0.1:8765/v1/chat/completions", "model": "qwen2.5:14b" },
  "vision": { "mode": "off" }
}
```

| 开关 | 关闭（默认） | 打开 |
|---|---|---|
| `ai.enabled` | 纯规则：按 `plan` 顺序走，0 网络请求 | 每步问模型；模型挂了自动退回规则 |
| `vision.mode` | 只发 JSON，不存图 | `multimodal`：每步存一张 `debug/state.png`，由本地代理读文件转 base64 |

`vision.mode` 之所以放在**代理进程**里编码，是因为脚本侧没必要碰图片，密钥也不该进脚本。

打开 AI 前还要两件事：调度器通用设置里启用 **JS HTTP 权限**；`manifest.json` 的 `http_allowed_urls` 加上你的地址（支持 `*` 通配）。

### 装了特别版就不用写这些

特别版把配置搬进了界面：**任务设置 → AI 代理（脚本）**，填服务地址、模型名、密钥，勾上启用即可，所有脚本共用一份。

此时脚本走 `ai.Chat()` 宿主通道，`config.json` 里的 `ai.endpoint` / `model` / `apiKey` 全部失效——也就不需要 JS HTTP 权限和 `http_allowed_urls` 了。密钥留在客户端进程里，脚本连读都读不到，`file` 也写不进仓库。

| 场景 | 通道 | 密钥位置 | 需要 HTTP 权限 |
|---|---|---|---|
| 特别版 | `ai.Chat()` | 客户端配置 | 否 |
| 官方版 | 脚本自己发请求 | `config.json` 明文 | 是 |

## 避障：三层，越往下越贵

| 层 | 机制 | 代价 | 有效性 |
|---|---|---|---|
| 路线层 | 预录 waypoint 绕开障碍，`move_mode` 标走/跑/跳/爬/游/飞 | 录制时的人力 | 最好，但要人走过一遍 |
| 执行层 | `TrapEscaper` 卡死脱困 | 免费 | 一般，靠随机试探 |
| 决策层 | 把截图丢给多模态问「往左还是往右」 | 一次几千 token | 兜底，只在前面都失败时用 |

执行层的真实逻辑（`PathExecutor.cs:916-941`、`TrapEscaper.cs:139`）：

1. 每 1 秒采样一次坐标，连续 8 帧位移 < 3 米 → 判卡死
2. 脱困动作按顺序循环：松 W → 下落 → 普攻 → 后退 1s → 左移 → 右移，每次叠加 30–45° 随机角度
3. 同一段卡死 3 次 → 抛 `RetryException`，整段放弃
4. 另有转向保护：偏角 > 5° 持续 2 秒 → 松 W 站定转完再走

**必须说清楚的**：BGI 没有视觉避障，也不做寻路。它不认识「前面是墙」，只是按点走、走不动就随机挣扎。所以复杂地形（森林、矿洞、多层建筑）会连撞 3 次然后放弃——这不是脚本写得不好，是机制上限。

AI 能补的只有最后一层：卡死 3 次后截一张图，问「前方是什么，绕左还是绕右」，然后生成一个偏移 20–30 米的新目标点。这属于**救火**，不要拿它当常规避障。

## 能力边界

| 约束 | 原因 | 应对 |
|---|---|---|
| `goto` 只走 150 米内 | 直线追踪不是寻路，远了必撞地形 | 超过就 `genshin.Tp` 传送到锚点附近，再走最后一段 |
| 传送是「最近锚点」不是精确落点 | `Tp` 会找最近的传送点 | 落点后按剩余距离再 `goto` |
| 室内 / 副本里读不到坐标 | `GetPositionFromMap` 依赖主界面小地图 | 用 `Bv.IsInDomain` 判断，切规则模式 |
| 坐标轴序 | BGI 世界坐标是 (横向, 纵向)，与游戏内 CSV 的 (纵向, 横向) 相反 | 从外部数据转坐标时 `x = Z, y = X` |
| 模型给了个离谱坐标 | 幻觉 | `maxGotoMeters` 拦一道，超限改走传送 |

## 接自己的模型

| 形态 | endpoint | 说明 |
|---|---|---|
| 本地 Ollama | `http://127.0.0.1:11434/v1/chat/completions` | 免费，7B–14B 够做「选动作」这种简单判断 |
| 本机中转（one-api / new-api） | `http://127.0.0.1:3000/v1/chat/completions` | 密钥留在代理进程，脚本只配回环地址 |
| 云 API 直连 | `https://api.deepseek.com/v1/chat/completions` | 必须 HTTPS；密钥会明文进脚本，**不要推送到公开仓库** |

模型只需要会输出 JSON，不需要 function calling。提示词里已经把动作 schema 写死了，`parseAction` 会做白名单校验，非法动作直接抛错退回规则。

## 推荐的推进顺序

1. **纯规则跑通**：把 `plan` 里的坐标填对，确认能走到、能按 F。这一步不需要任何模型。
2. **AI 只做选择**：`plan` 给 2–3 个候选点，让模型选下一个去哪个。动作空间小，7B 模型就够。
3. **放开坐标**：允许模型给 `goto` 的 x/y，靠 `maxGotoMeters` 兜底。
4. **多模态兜底**：只在前三步都失败时开 `vision.mode`，用一次贵一次。

一次跳到最后一步，通常结果是「模型给了个看着对、实际撞墙的坐标」，然后你以为是自己配置错了。
